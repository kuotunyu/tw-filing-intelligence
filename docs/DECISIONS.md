## D-001 Python 3.13 + uv（**不是** 3.11，原因是非 ASCII 路徑）

- **決策**：Python 3.13（`>=3.13,<3.14`），uv 管理環境與 lockfile。
- **理由**：
  1. 本機系統 Python 是 3.10.9 且無 CUDA torch → 用 uv 建獨立環境，不污染系統。
  2. **關鍵限制**：本 repo 位於 `...\CC_github部隊\...`，路徑含非 ASCII 字元。
     editable install 產生的 `_editable_impl_tw_filing_intelligence.pth` 內含
     UTF-8 編碼的絕對路徑，而 **Python ≤ 3.12 的 `site` 模組用系統 locale
     （本機為 cp950）讀取 `.pth`** → venv 一啟動就
     `UnicodeDecodeError: 'cp950' codec can't decode byte 0xe9`，
     `uv run` 完全不能用。Python 3.13 起 `.pth` 以 UTF-8 讀取，問題消失。
     實測：3.11 → 壞；3.13.13 → 正常（`uv run python -c "import twfi"` 通過）。
  3. 3.13 對 PyMuPDF / pdfplumber / duckdb / torch / transformers 都已有輪子。
- **替代**：
  - 3.11 ＋ 全域 `PYTHONUTF8=1`（脆弱，依賴使用者環境變數）
  - 3.11 ＋ 非 editable 安裝（改一行程式就要重裝）
  - 把 repo 搬到純 ASCII 路徑（不在本任務授權範圍，且會動到使用者的目錄結構）
- **影響**：README 的 Quickstart 標示 Python 3.13。若日後把 repo 移到 ASCII 路徑，
  可下修版本需求，但沒有必要。
- **狀態**：ACCEPTED (2026-07-31)

## D-002 Parser：baseline = PyMuPDF plain，candidate = in-repo layout-aware

- **決策**：只比較兩個 parser。baseline 為 PyMuPDF `get_text()` ＋ 固定 chunk；
  candidate 為**本 repo 內自建**的 layout-aware parser
  （PyMuPDF dict-mode blocks ＋ 字級/字重 heading 分群 ＋ reading order ＋
  pdfplumber 表格 ＋ 向量繪圖密度 figure 偵測）。
- **理由**：
  1. Protocol 要求最多兩個 parser、不做 parser 排行榜。
  2. 台灣年報是 digital-born PDF，native text layer 完整，瓶頸在**結構**
     （heading 階層、跨頁表、單位列、圖表區）而不是 OCR。
  3. 自建 parser 讓「所有程式碼存在本 repository」成立，且**完全 deterministic**、
     可用合成 PDF fixture 離線測試、不需要下載額外 layout 模型。
- **替代**：`docling`（需下載 layout/TableFormer 權重、Windows 依賴較重、
  非 deterministic）、PaddleOCR PP-Structure（Windows 安裝痛點）。
  兩者列為 **out of scope**，並在 report 中說明「本輪未驗證 learned layout model」
  這個限制。
- **影響**：結論不能延伸為「learned layout parser 沒用」，只能說
  「rule-based structure-aware parsing 已足以產生 X 的增益」。
  這個限制必須寫進 `docs/FEASIBILITY_REPORT.md`。
- **狀態**：ACCEPTED (2026-07-31，使用者確認)

## D-003 模型：`qwen3.6:27b` 同時擔任 generation 與 VLM

| 角色 | 模型 | backend | 精度 |
|---|---|---|---|
| Embedding | `BAAI/bge-m3` | HF transformers（cache 已存在） | fp16 |
| Reranker | `BAAI/bge-reranker-v2-m3` | HF transformers（cache 已存在） | fp16 |
| Generation ＋ VLM | `qwen3.6:27b` digest `a50eda8ed977` | ollama 0.32.0（已 pull） | Q4_K_M |

- **決策**（使用者 2026-07-31 拍板）：⑤A 的正式主候選是 `qwen3.6:27b`，
  **文字與圖表共用同一個模型**；數值答案由 SQL 完成；
  `qwen3-vl:8b` 只在 freeze 前做小型 chart challenger（見 D-009）；
  `gpt-oss:20b` 不進正式 pipeline。
- **可行性已實測**：`ollama show qwen3.6:27b` 回報
  `capabilities: completion / vision / tools / thinking`、`architecture qwen35`、
  `27.8B`、`Q4_K_M`、`context length 262144`。
  **確認具備 vision**，因此「同一模型處理文字與 chart crop」成立；
  若它是純文字模型，chart route（必須從 original crop pixels 讀值）就不可能實作。
- **理由**：
  1. 全部**零新下載**（HF cache ＋ ollama 皆已有）。
  2. 27B 通才對繁體中文長篇年報敘述的理解優於 8B，而 chart crop 讀值由同一模型
     承擔可避免第二套權重佔 VRAM。
  3. 數值不靠模型（D-005），所以 Q4 量化對「數值正確率」這個主指標的風險有限。
- **替代**：`Qwen/Qwen3-VL-8B-Instruct` bf16（HF，品質未必更好且需兩套權重）、
  `Qwen3-4B-Instruct-2507`（太小，會拖低 candidate 使 gate 判斷失真）。
- **固定設定**：`temperature=0.0`、`top_p=1.0`、`top_k=1`、`seed=20260731`、
  `num_predict=512`、`num_ctx=8192`、**`think=false`**。
  關閉 thinking 的理由：長度不可預測的推理段落會讓 generation p95 latency 與
  token 計數不可比較，而數值推理本來就走 SQL。
- **已知風險**：VRAM 約 20–21GB（17GB 權重 ＋ KV cache ＋ 2.2GB 檢索模型），
  G10 的 22GB 上限餘裕不大。上限是依硬體設定，**不因換模型放寬**。
- **狀態**：ACCEPTED (2026-07-31，使用者確認)

## D-005 Numeric route 不允許 LLM 自由生成 SQL

- **決策**：只用 templated、參數化 SQL（lookup / delta / ratio / growth），
  由 router 決定 template ＋ 參數。
- **理由**：protocol 要求 deterministic；自由生成 SQL 會引入不可重現的失敗模式，
  也讓「數值正確率」不可歸因。
- **影響**：無法回答 template 未覆蓋的數值問題 → 這類題目走拒答，並在
  error analysis 標為 `template_miss`（誠實記錄能力邊界）。
- **狀態**：ACCEPTED (2026-07-31)

## D-006 Chart caption 只進 index

- **決策**：VLM caption 寫入檢索索引；**最終數值答案必須**來自 original crop pixels
  或結構化資料。程式層面以 answer provenance 檢查強制（有測試）。
- **理由**：caption 是有損摘要，直接當數值來源會產生無法追溯的幻覺。
- **狀態**：ACCEPTED (2026-07-31)

## D-007 Router 不做 agent loop

- **決策**：single-pass typed classification ＋ 最多一次 bounded correction。
- **理由**：protocol 明確禁止無上限 loop；latency 與成本可預測；失敗可歸因。
- **狀態**：ACCEPTED (2026-07-31)

## D-008 LLM-as-judge 不參與 gate

- **決策**：judge 只用於 `evidence_sufficiency` 的輔助觀察，不進入任何 GO／NO-GO 判定。
- **理由**：避免用同一家族模型自我評分造成的樂觀偏誤。
- **狀態**：ACCEPTED (2026-07-31)

## D-009 Chart challenger：freeze 前一次性模型決策，規則事前寫死

- **決策**：`qwen3-vl:8b` digest `901cae732162` 只作為 chart route 的 challenger，
  在 **DEV 文件上**跑一次 16 題 chart crop 讀值比較
  （`data/evaluation/dev/chart_challenger.jsonl`），依**事前規則**決定 locked run 的
  chart route 用哪個模型：
  > 若 `qwen3-vl:8b` 正確率高出 `qwen3.6:27b` **≥ 10 個百分點**（16 題中至少多對 2 題），
  > chart route 改用 `qwen3-vl:8b`，其餘 route 仍用 `qwen3.6:27b`；否則全部用 27B。
- **理由**：使用者要求保留一個小型 chart challenger。但「跑完再看要用哪個」在
  方法論上等於事後換模型，除非**規則、資料、時點都事先固定**。因此：
  規則寫死在 protocol §2.3、只用 DEV 資料、只在 freeze 前執行一次、
  結果無論輸贏都要公開在 report。
- **限制**：challenger 不進入 locked evaluation、不列入 F0…F7 ladder、
  locked run 只用一個 chart 模型。freeze 之後**不得再比較模型**。
- **狀態**：ACCEPTED (2026-07-31)

## D-010 資料取得策略（P1 實測後修訂）

- **決策**：
  | 資料 | 取得方式 | 自動化？ |
  |---|---|---|
  | TWSE OpenAPI（公司基本資料、**當期**財報、營益分析、EPS、月營收） | `scripts/fetch_twse_openapi.py` | ✅ 全自動 |
  | 年報 PDF（7 份） | **人工放置** `data/raw/manual/` ＋ SHA-256 驗證 | ❌ 刻意不自動化 |
  | MOPS XBRL（7 份，FY2023／FY2024） | **人工放置**（建議但非必要） | ❌ |
  | 歷史結構化數值 | XBRL 優先；未提供時退回**已驗證的表格擷取值** | — |

- **理由**（完整證據見 `docs/DATA_PROVENANCE.md §8`）：
  1. **OpenAPI 是單期快照**。實測 `t187ap06_L_ci` 回 1045 列全部 `年度=115 季別=1`。
     原本 P4「用 OpenAPI 當歷史數值來源」的假設是錯的，必須修正。
  2. **新版 MOPS 是 JS SPA**。`/mops/web/*` 只回 65 bytes 的 JS bootstrap；
     要取資料就得呼叫未公開 XHR API → 協議禁止。
  3. **`doc.twse.com.tw/server-java/t57sb01` 沒有 CAPTCHA 但是 POST 表單**，
     `step` 語意未公開 → 驅動它屬於表單模擬／逆向，且只為 7 份文件不值得。
- **對 G1 的影響**：無。人工放置 ＋ `source_page` ＋ SHA-256 完全可重現，
  且不依賴破解或私人 endpoint —— 這是**符合** G1 的取得方式。
- **對研究結論的限制**（必須寫進 report）：
  - FY2023／FY2024 的結構化數值若未提供 XBRL，來源是**我們自己的表格擷取**
    而非官方 XBRL。RQ2（deterministic SQL vs LLM 猜）仍然成立，
    但「官方結構化資料」這個更強的說法要降級為「已驗證的結構化資料」。
  - 「臺灣公開資訊在文件層級沒有穩定官方批量下載介面」本身是 feasibility 發現。
- **狀態**：ACCEPTED (2026-07-31，P1 實測後)

- **決策**：既然 OpenAPI 只有當期，就不當歷史來源，而是當

  正好用來測 unit accuracy。

## D-012 協議修訂：新增 3 份 FY2024 財務報告書（7 → 10 份文件）

- **背景（實測發現，非事前預期）**：
  1. **從 FY2024 起，股東會年報不再內含合併財報。** MOPS 對該年度只列**一個**檔案，
     所以不是分檔上傳，是財報變成**另一份申報**（資料類型「財務報告書」→
     細節「IFRSs合併財報」→ 季別「第四季」）。結果頁甚至直接提供
     「查詢財務報告書」按鈕。
     - `2330-FY2024-AR`（91 頁）：有 `公司治理`／`風險事項`，**0 個財報標記**
     - `2882-FY2024-AR`（248 頁）：同樣 **0 個財報標記**
  2. **`2317-FY2024-AR` 文字層不可用。** 抽出 118,681 字元，但
     `公司`／`年度`／`財務`／`營業`／`股東`／`董事` **一個都沒出現** ——
     嵌入字型缺 ToUnicode 對照表，抽出的是 glyph code。
- **決策**：
  - **新增** `2330-FY2024-FS`、`2317-FY2024-FS`、`2882-FY2024-FS`
    （`doc_type: financial_report`）→ 宣告文件 **7 → 10 份**，仍在協議的 5–10 份內。
    實測三份皆 **usable，3/3 財報標記齊全**（124／202／402 頁）。
  - **保留** `2317-FY2024-AR` 在宣告清單中，標記 `usable=False` 並記錄原因，
    但**不從它出題**。
- **為什麼保留不可用的文件**：「7 份公開年報中有 1 份文字層不可用」
  本身就是 feasibility 發現。刪掉紀錄等於刪掉發現。
  `twfi.protocol.DECLARED_DOCUMENTS` 用 `usable` 欄位區分，
  `USABLE_DOCUMENTS` 才是出題來源。
- **為什麼這反而是更好的設計**：真實分析師本來就得同時讀年報（敘述）與財報（數字）。
  這個修訂讓 pipeline 更貼近真實工作流，並天然產生 `cross_document` 題型的場景。
- **合法性**：協議此時仍為 `1.0.0-draft`，**未 freeze**，因此修訂合法。
  Freeze 之後同樣的修訂就必須改 `protocol_version` 並重跑全部 locked evaluation。
- **每家 locked 公司仍有兩個年度的可用證據**：
  FY2023 完整年報 ＋ FY2024 財報（2330／2317／2882）。
- **狀態**：ACCEPTED (2026-07-31，資料取得後)

## D-014 Chart route 的圖表候選規則（取代任意上限）

- **問題**：向量分群在 8 份可用文件上找到 **1,744 個圖表區**。
  若全部送 VLM 生 caption，以每張 ~5 秒估算是 **~145 分鐘** GPU 時間，
  而且大部分是不該進 chart route 的東西。
- **先量測再決定**（不是先設上限）：
  - 只用「附近有數字標籤」過濾 → 1,744 → 1,359（**僅減 22%**）。
    原因：財報頁面到處都是數字，這個特徵分不開。
  - 檢查分布後發現真相：得分最高的「圖表」是 **253 個數字標籤、529 條路徑、
    31 萬面積** —— 那是**有框線的表格**。向量分群找到的大多是表格格線，
    而表格在每個密度指標上都**贏過**真圖表。
- **決策**：`chart_candidates()` 依序套用兩個排除：
  1. **與已偵測表格重疊 ≥50% 的區域是表格**，不是圖表。
     判準來自 pdfplumber 自己的輸出，不是另一組門檻。
  2. **附近沒有數字標籤的是裝飾**（logo、封面美術、分隔線）。
  順序很重要：只用 (2) 會留下表格而丟掉真圖表。
- **量測結果**：**1,744 → 503**（減 71%），caption 成本 ~145 分 → **~42 分**。
  因此**不需要任意上限**。
- **不得無聲截斷**：`AssembledDocument.discarded_figures` 記錄被排除的數量，
  並進入 parse stats。brief 要求「若 pipeline 限制了覆蓋範圍，必須 log 被丟掉的東西」。
- **限制**：這個規則會漏掉「沒有數字標籤的圖表」（純示意圖、流程圖）。
  那類圖本來就答不出數值題，但若 locked set 有 chart_value_trend 題目落在
  這種圖上，會被記為 retrieval 失敗而非資料限制 —— 標註時必須避開。
- **狀態**：ACCEPTED (2026-07-31，量測後)

## D-015 數值層：不猜單位，不挑來源，不寫自由 SQL

- **不猜單位**：`t187ap14_L`（各產業EPS統計）的 `營業收入` 欄位**沒有任何單位標註**。
  TWSE 財務數據慣例是千元，但「慣例」是猜測。該欄位以 `unit=None` 載入 →
  `LineItem.is_usable` 為 False → 任何計算都會被 `UnitMismatchError` 擋下。
  **載入但不可用**比「假設千元」誠實：後者會產生一個看起來正確、實際錯 1000 倍的數字。
- **不挑來源**：同一個 `(公司, 期間, account)` 可能有多筆。
  `store.require()` **拒絕自行選擇**，並在錯誤訊息中列出每個候選的
  `statement/unit=value (source)` 與消歧方式。實測觸發：2330 的 `營業收入`
  同時存在於損益表（千元）與營益分析（百萬元）。
- **不寫自由 SQL**：只有 5 個 template（`lookup`／`difference`／`growth_rate`／
  `ratio`／`cross_source_check`）。router 只能選 template 並填參數。
  template 未覆蓋的問題是 `TemplateMissError` —— 一個**可計數的能力邊界**，
  而不是一個無法重現的錯誤答案。
- **金控的發現要更精確**：不是「金控沒有營業收入」，而是
  **「它的損益表沒有這一行，但一個彙總 endpoint 合成了一個，兩者不是同一個量」**。
  實測：`t187ap14_L` 對 2882 回報 `營業收入 = 72,538,053`（無單位），
  而 `t187ap06_L_fh` 完全沒有這個欄位。
  跨公司比較這兩個數字會錯，而且**沒有任何單位檢查抓得到**——
  這是為什麼 account 詞彙表按 statement 分開。
- **產業分類只信該信的來源**：`_ci`／`_fh` 是 TWSE 按產業分開發布的，有權威性；
  `t187ap17_L`／`t187ap14_L` 是跨產業彙總。若讓後者決定產業別，
  2882 會被重新標記為一般業，抹掉整個 hard case。
  `DatasetSpec.declares_industry` 記錄這個區別。

## D-016 Gold 標註：作者只能是人，來源不能是被測的抽取器

- **問題**：協議要求 `annotator = "human"`，但實作是由 LLM（Claude）協助進行的。
  若由 LLM 產生答案再蓋上 `human`，那是**偽造整個研究賴以成立的欄位** ——
  比任何程式 bug 嚴重，因為它讓事前註冊變成裝飾，而報告會包含一句假話。

- **更尖銳的問題（實作時才發現）**：協議原本只禁「gold 不得由 candidate system 產生」，
  但真正的陷阱在別處。**若 `table_cell` 的 gold 值來自本 repo 自己的表格抽取器，
  它與正在被評測的 F1／F4 因子是循環的**：抽取器抽錯 → gold 錯 → candidate 用同一個
  抽取器 → 它會「答對」一個錯答案。量到的增益是「用 parser 評測自己」的假象。
  這個循環**沒有任何單元測試抓得到**，因為兩邊都「一致」。

- **決定**：
  1. `GoldRecord.annotator` 的型別是 `Literal["human"]`。沒有第二個可填值，
     所以沒有任何程式路徑（包括之後趕時間寫的）能產生機器署名的 gold record。
  2. 新增 `answer_provenance`，只允許 `human_read_pdf` 與 `official_structured`。
     **本 repo 的抽取器在型別上不可表示** —— 不是「不建議」，是寫不出來。
  3. 草稿走另一條型別 `DraftItem`，**根本沒有 `answer` 欄位**。
     它是「指向證據的指標」，不是「少填一欄的 gold record」，不能靠加 key 升級。
     草稿檔在 `data/evaluation/worklist/`，與 gold 檔分離。
  4. `parse_record` 對 `annotator != "human"` 直接 raise，並在錯誤訊息裡說明
     草稿該放哪裡 —— 讓下一個人不必重新推導這個結論。

- **分工**：判斷類題型（narrative／chart／cross_page／cross_document／unanswerable／
  table_cell／cross_period_comparison）由人對照原始 filing 產生答案。
  只有 `numeric_calculation` 可由官方 OpenAPI 機械建置並自動重驗 ——
  該答案的真值任何人都能重跑查驗，人工轉錄只會增加錯誤而非增加準確度。
  工具負責預填機械欄位與切出證據 crop，**不得產生答案**。

- **推論出的限制**：`cross_period_comparison` 需要 FY2023 vs FY2024，
  但 OpenAPI 只有當期快照（D-011／§8 發現 1）→ 這 4 題的歷史值只能是 `human_read_pdf`。

- **狀態**：ACCEPTED (2026-07-31，使用者拍板「按題型分工」)

## D-017 可讀性的分母錯了，而題型能力必須逐份文件量測

- **怎麼發現的**：不是靠 review，是靠一個「不該是零」的結果。標註工具在
  `2330-FY2023-AR` 找到 5 個證據 slot，在 `2330-FY2024-FS` 找到 **0 個** ——
  而那份文件整本就是報表。追下去才發現文件本身的問題。

- **儀器的錯**：`quality.py` 的 `readable_ratio` 分母是 `pages_with_text`。
  完全沒有文字的頁面**同時離開分子與分母**，所以**任何數量的純圖片頁都無法拉低分數**。
  這個儀器**結構上偵測不到純圖片頁**。它把 `2330-FY2024-FS` 判為 **100% 可讀**。
  更糟的是，`tests/test_quality.py` 有一個測試叫
  `test_blank_pages_do_not_count_against_readability`，**把這個 bug 寫成了預期行為**。

- **文件的事實**：`2330-FY2024-FS` 有 11 頁無文字層，最長連續段 **pp.7–15（9 頁）**。
  以財報排版位置，那是**四大報表** —— 夾在會計師查核報告與附註（p18「編製基礎」）之間。
  修正後：**91% 可讀**，判定 `statements_not_machine_readable`。

- **這是可行性發現，不是麻煩**：只讀報表表格的系統在這份文件上找不到 FY2024 營收；
  讀附註的系統找得到 —— 它在 **p55「附註二一 營業收入」**，旁邊就是 FY2023 比較數。

- **修法**（兩個比率各司其職，因為它們測的是不同的失效）：
  - `readable_ratio` 分母改為**全部頁數** —— 沉默必須算進去。
  - `legible_text_ratio` 保留舊分母，回答較窄但仍有用的問題：**有文字的頁面裡有幾成看得懂**。
    亂碼會動這個數字，缺文字層不會。
  - 新增 `image_only_runs` 與 `statements_not_machine_readable` 判定。
    **長度比數量重要**：散落的空白頁是封面與隔頁，連續一打是抽不到的結構區塊。

- **題型能力逐份量測**（`scripts/check_question_sources.py` ＋ `eval/sources.py`）：
  單一 `usable` 旗標太粗，無法拿來出題。我的第一版推導有三個錯，都是量測後才發現：
  1. **忽略文件層級判定** → `2317-FY2024-AR`（**0 頁可讀**）拿到 2 個題型，
     因為抽取器在壞掉的文字層上仍「找到」66 個表格與 47 個圖表。
     **那些是亂碼格線與無標籤線稿，是 artefact 不是證據。**
     現在判定是閘門，在讀任何計數之前就先擋。
  2. **把「報表不存在」與「報表不可讀」混為一談** → `2330-FY2024-AR` 被標成文字層有問題，
     但它是 FY2024 股東會年報，**依設計就不含報表**（D-012）。
     改為三態 `readable / image_only / absent_by_design`。
  3. **單位門檻沿用表格門檻** → `2330-FY2024-FS` 以 3 個帶單位表格通過數值題，太薄。
     實測十份文件：帶單位表格 0–104，表格總數 55–513 —— **多數抽出的「表格」是排版而非報表**。
     單位門檻獨立為 5。

- **對 P5 的實際約束**（`results/runs/question_sources.json`）：
  - **鴻海只有 `2317-FY2024-FS` 能出題**，兩份年報歸零 →
    2317 的 narrative 題只能來自財報附註散文，不是年報敘述。
  - **`2330-FY2024-FS` 不能出數值題** → 2330 的數值題須來自 `2330-FY2023-AR`（30 個帶單位表格）。
  - `unanswerable` **不是文件屬性**，任何文件的能力清單裡都不會有它。
    而且能力最差的文件是最糟的取材處 —— 拒答會因為錯誤的理由而正確。

- **狀態**：ACCEPTED (2026-07-31，protocol 尚未 freeze，依量測修正)

## D-018 單位宣告是文件範圍的，不是表格範圍的

- **怎麼發現的**：標註 PROBE-0003 時，使用者在 `2330-FY2024-FS` p55（附註二一 營業收入）
  上找不到任何單位字樣，只看到數字左邊有 `$`。他問「這一頁沒有寫單位」——
  這個問題直接命中一個設計缺陷。

- **事實**：單位宣告在 **p16**，附註章節的開頭，原文是
  **「合併財務報告附註 民國113及112年度（除另予註明者外，金額為新台幣仟元）」**。
  它涵蓋**其後所有附註表格**。p55 距離宣告處 **39 頁**。

- **後果**：`tables.py` 的 `detect_unit()` 是在**表格局部**找「單位：」樣式。
  對這份文件，它在 p55 什麼都找不到 → 判定單位未宣告 → 該表不可用。
  這正好解釋了 D-017 量到的一個數字：
  **`2330-FY2024-FS` 的 65 個表格只有 3 個宣告單位**。
  不是文件沒寫，是**偵測範圍太窄**。

- **為什麼這不是小問題**：它會讓數值層系統性地低估可用表格數，
  而低估的方式是「安全的」（拒答而非答錯），所以**不會有任何測試失敗**，
  只會讓能力看起來比實際差。D-015 的「不猜單位」是對的，
  但「找不到宣告」與「沒有宣告」是兩回事，先前混為一談了。

- **已修**：`document_unit()` 掃描文件層級宣告，`inherit_units()` 套用到後續表格。
  判準是**限定詞**：「除另予註明者外」本質上是對整個章節的宣告，
  表格上方那種不帶限定詞的 `單位：新台幣仟元` 才是局部的。
  只**向前**繼承 —— 宣告之前印出的表格不在其範圍內，維持單位未宣告。
  `UnitSpec.scope` 與 `declared_on_page` 保留「局部宣告 vs 文件繼承」的區別，
  因為繼承是推論不是閱讀，信心較低；`declared_on_page` 也讓答案能引用
  那個讓數字可解讀的頁面（PROBE-0003 正好需要）。

- **量到的效果**（帶單位表格數）：

  | 文件 | 修前 | 修後 | 繼承 | 宣告頁 |
  |---|---|---|---|---|
  | `2330-FY2024-FS` | 3 / 65 | **64** | 62 | p16 |
  | `2882-FY2024-FS` | 104 / 240 | **239** | 137 | p13 |
  | `2330-FY2023-AR` | 30 / 193 | **140** | 110 | p110 |
  | `2317-FY2024-FS` | 12 / 113 | 12 | 0 | 無 |

  **鴻海沒有全域宣告**，它在每一頁報表標題各寫一次 —— 那是發行人排版習慣的差異，
  不是缺陷，局部偵測本來就抓得到。

- **連帶修掉一個更危險的 bug**：查證鴻海時發現它的例外寫法跟國泰金不同 ——

  ```
  2882-FY2024-FS p10   單位：新台幣仟元，惟每股盈餘為元
  2317-FY2024-FS p14   單位：新台幣仟元(除每股盈餘為新台幣元外)
  ```

  `_UNIT_EXCEPTION` 只認第一種。對第二種它回報 `exception=None` →
  `is_uniform=True` → **數值層會放心地把千元套到每股盈餘上，錯一千倍**。
  這正是整個單位設計要防的錯誤，而它一直是活的，只因為先前取樣的文件剛好是另一種寫法。
  **只匹配第一份樣本的寫法，就是單位檢查會「通過但錯誤」的方式。**

- **對 P5 的影響**：`2330-FY2024-FS` 因此**可以出數值題了**（D-017 原本的限制解除）。

- **狀態**：ACCEPTED ＋ 已實作 (2026-07-31，標註時由使用者發現)

## D-019 Gold 改為「模型起草 ＋ 人工抽樣稽核」，並把這件事寫在臉上

- **問題**：D-016 要求 `annotator` 必須是 `human`。實際做了 24 題之後，
  使用者明確表示「煩死了，我不想再做了」。剩下 48 題在那個規則下**不會完成**，
  而**跑不完的研究量不到任何東西**。

- **重新檢視紅線**：真正的循環風險有兩個，而且都很具體 ——
  1. 答案不能來自 **candidate**（`qwen3.6:27b` ＋ 檢索 pipeline）
  2. 答案不能來自**本 repo 的抽取器**（那是 F1／F4 要測的東西）

  **一個不同的模型讀渲染出來的頁面像素，兩條都不違反。** 它不是 pipeline，
  也不經過文字層。而在「抄數字」這件事上人並不更可靠：
  目前唯一一個錯的答案 PROBE-0004 是**人工轉錄錯**，由機器檢查抓出來。

- **人真正不可取代的是「選題目」**，不是「讀數字」。
  一個同時寫問題和答案的標註者，可能無意識地偏向 pipeline 擅長的題型 ——
  而記錄本身不會顯示這件事。

- **決定**：
  1. `annotator` 改為 `Literal["human", "claude-opus-5"]` ——
     **具名，而不是斷言**。讀者要能自己權衡。
     **candidate 在型別上不可表示** —— 被測系統永遠不能提供自己的 gold。
  2. 新增 `answer_provenance = "model_read_rendered_page"`。
     模型**只准**讀渲染像素，不准讀文字層。
     `record_problems` 拒絕「模型起草卻聲稱 human_read_pdf」的記錄。
  3. 新增 `audited: bool` —— 是否有人親自對照頁面查過這一筆。
  4. **抽樣必須不可挑選**：`scripts/audit_gold.py` 用協議的 decoding seed
     （20260731）抽樣，先按 id 排序再抽，所以**起草者無法影響抽到哪些**，
     任何人都能重新推導出「本來該被查的是哪幾筆」。
     拿一份手挑的「樣本」會被看出來。
  5. `composition()` 回報 human／model_drafted／audited 的組成，
     **報告必須逐字印出這組數字**。
  6. 整組都是模型起草且**完全沒稽核**時，`set_problems` 直接報問題 ——
     那種狀態下沒有任何東西在防止選題偏差。

- **代價（必須寫進報告，不得省略）**：gold 由 LLM 起草、人工抽樣約 25%。
  讀者可據此折扣。這比原方案弱，但**比一份永遠做不完的研究強**。

- **不改的部分**：`chart_value_trend` 5 題仍建議人工 ——
  「LLM 讀圖表」對「LLM 讀圖表」是最接近循環的組合。

- **狀態**：ACCEPTED (2026-07-31，使用者在做完 24 題後拍板)

## D-024 抽取文字一律做 NFC 正規化（不是 NFKC）

- **怎麼發現的**：要為 dev 出題，先檢查兩份 dev 文件的文字層品質，
  結果**兩份都是壞的，而且壞法完全不同**。

- **兩種損壞**：

  | 文件 | 現象 | 可救嗎 |
  |---|---|---|
  | **1301-FY2023-AR** | 年 存成 **U+F98E**、度 存成 **U+FA01**（CJK 相容表意文字）—— 畫面上看起來完全正確，但**不等於** U+5E74／U+5EA6 | ✅ **NFC 可救** |
  | **2412-FY2023-AR** | 64,238 個字元散布在 Cyrillic／Armenian／Syriac／Ethiopic／Tibetan —— subset font 沒有 ToUnicode 的原始 glyph index | ❌ **救不回**（實測 NFC 救回 0 頁） |

- **1301 的實際代價**：字串 `「年度」` 在該文件 **91 頁**上完全不存在，
  而讀者在每一頁都看得到它。BM25 比不到、dense 會去 embed 一個罕見 codepoint、
  `tables.py` 的單位宣告 regex 不會觸發、`verify_gold_answers` 會把正確答案判成 absent。
  **這四件事看起來全都像檢索或標註失敗，但一件都不是。**

- **決策**：在**抽取邊界**做 `unicodedata.normalize("NFC", ...)`，
  位置是 `src/twfi/parsing/normalise.py`，套用在
  `baseline.py`（F0）、`layout.py`（candidate）與 `tables.py` 三處，
  以及 `verify_gold_answers.py` 的比對兩側。
  **實測：1301 的 91 頁全部救回（0 → 91）。**

- **為什麼是 NFC 而不是 NFKC**：
  相容表意文字有**正規分解**，NFC 就夠。而 NFKC 會**連帶改寫全角形式** ——
  `：`→`:`、`（`→`(`、`，`→`,`。本 repo 有好幾處**字面比對中文標點**
  （例如 `tables.py` 的 `_UNIT_EXCEPTION` 字元類是 `[^，。、）)]`），
  NFKC 會**在離這裡很遠的模組裡默默改變 regex 的行為**。
  我第一版寫的就是 NFKC，`test_layout_parser.py` 的三個 end-to-end 測試立刻擋下來
  （fixture 的 `單位：` 變成 `單位:`）—— **那不是 fixture 過時，是打擊面太大**。
  實測 NFC 救回的頁數與 NFKC **相同（91 頁）**，多出來的廣度沒買到任何東西。

- **公平性**：**baseline 與 candidate 兩邊都套**。
  相容字損壞是**語料的性質，不是被測的 factor**；只修 candidate 那一側，
  它就會變成 candidate 的增益。要嘛兩邊都修，要嘛兩邊都不修。

- **readability 指標對這個 bug 完全無感**（值得單獨記一筆）：
  1301 正規化前後 `readable_ratio` 都是 95.9%，因為 anchor 有 11 個詞，
  那些頁面用**別的** anchor（公司、財務）在正常字體裡通過了。
  所以 anchor 測試**在原理上偵測不到這一類**，這也是為什麼它必須被記成發現，
  而不是被當成指標修正。

- **我今晚在這條上犯的錯（一併記下）**：我先寫了一個「壞字偵測器」，
  用 codepoint 範圍黑名單。它**兩個方向都錯**：
  範圍表漏了 U+2C00–2E7F（我自己舉的例字 `Ⳋ` 就在洞裡），
  而且**把 1301 評為 0% 損壞**，而 1301 恰好是 25% 頁面壞掉的那一份。
  我把它**整個退掉**，沒有端出第三個版本 ——
  在使用者睡覺、無法仲裁的時候，端一個我知道是錯的指標，
  就是 D-017／D-020 的同一個錯誤再犯一次。
  **一個可信的壞字偵測器仍是待辦，且必須先想清楚「合法字元」的白名單。**

- **2412 的限制必須寫進 report**：它是 **dev 文件之一**，
  64,238 個字元不可還原。F0 baseline 在它的部分散文上必然失敗，

## D-026 模型放哪張處理器：embedder 上 CPU、reranker 上 GPU（而且 top-k 被 VRAM 綁住）

- **問題**：D-025 量到三個模型同時駐留是 **21.91 GiB**，G10 硬限 22 GB —— 餘裕 90 MB。
  R3 原本的緩解方案是「必要時把檢索模型 offload 到 CPU」。**那個方案量下去是死的。**

- **實測（全部在本機、CPU 部分 `torch.set_num_threads(6)`）**：

  | 配置 | VRAM | 檢索延遲 | G10 |
  |---|---|---|---|
  | 三個模型都在 GPU | 21.91 GiB | rerank top-50 157 ms | ❌ 餘裕 90 MB |
  | **reranker 移到 CPU** | ~19 GiB | **top-10 5.85 s**／top-30 30.75 s | ❌ **超過 3s 上限近兩倍** |
  | **embedder→CPU、reranker+generation→GPU** | **21.07 GiB**（top-20） | **rerank 61 ms**、query embed 55 ms | ✅ **餘裕 +0.93 GB** |

- **決策**：**embedder 放 CPU，reranker 放 GPU。** 分工與直覺相反，但量測很清楚：
  1. **embedder 在查詢時只 embed 一個查詢** → CPU **55 ms**，而它在 GPU 上要吃約 2 GB。
  2. **reranker 是在 CPU 上會爆掉的那個** → GPU 61 ms vs CPU 5.85 s，**快 96 倍**。
     原因是工作量形狀不同：reranker 要對 top-k 個 (query, chunk) pair 各跑一次
     512-token 的 cross-encoder，那是 k 倍的計算量；embedder 只跑一次。
  3. **embedder 只有「建 index」時需要 GPU**，那是一次性的（實測 13,953 chunks 約 75 秒），
     且建 index 時 generation model 不必駐留，所以那一階獨佔顯卡也沒問題。

- **必須寫進 report 的限制：top-k 是被記憶體綁住的，不是被檢索品質決定的。**

  | top-k | VRAM | 餘裕 |
  |---|---|---|
  | 20 | 21.07 GiB | +0.93 GB |
  | 30 | 21.31 GiB | +0.69 GB |
  | 50 | 21.70 GiB | +0.30 GB |

  也就是說「要取多少候選」這個決定，在這張卡上**先撞到記憶體才撞到品質**。
  報告不得把 top-k 呈現為自由選擇的超參數。
  （附帶說明：PyTorch 的 caching allocator 不歸還記憶體，所以上表是**累積高水位**，
  同一個 process 內先跑過 top-50 會抬高後續讀數。作為 G10 的 peak 量測是正確的，
  作為「單獨跑 top-20 會用多少」則是上界。）

- **G10 是 soft gate**，所以即使超過也是 CONDITIONAL_GO 不是 NO_GO。
  但**不因此放寬 G10** —— 那三個數字來自顯卡，不是來自模型想要多少（協議 4 明文）。

- **這也是一個 production 與 feasibility 的分野，要如實寫**：
  批次評估可以把「檢索階段」與「生成階段」分開跑，各自獨佔顯卡；
  一個真的線上服務兩者必須同時駐留，那在這張卡上**過不了 22 GB**。
  本研究能證明的是前者。

- **狀態**：ACCEPTED (2026-08-01)

## D-027 表格抽取策略：`text` 在 dev 文件上一個已知數字都取不到

- **怎麼發現的**：要寫 P4 的 loader，先看抽取器在 `1301-FY2023-AR` p188 上抽到什麼 ——

- **我第二個量測踩到更嚴重的線**：改用「gold 裡已知正確的數字能不能被抽回來」當標準是對的，

  | strategy | 抽回 | 只有它抽回 |
  |---|---|---|
  | **`text`（現行）** | **0/15（0%）** | 0 |
  | `lines` | **9/15（60%）** | 9 |
  | 聯集 | 9/15 | — |
  | 兩者都抽不到 | 6 | （可能本來就在散文裡，或該頁無文字層） |

  這本身是語料異質性的發現，值得寫進 report。

  1. dev 證據支持（聯集 ≥ lines ≥ text）。
  2. **沒有任一 strategy 支配另一個**，所以「兩個都跑、全都收」是先驗上最穩健的選擇，
     不需要知道哪個 split 偏好哪一種 —— 而「只用 `lines`」就是在對 dev 過度擬合。
  3. 現狀是 **dev 上 0% 的功能性失效**，這不是「調到有利」，是讓元件能運作。

- **改預設前必須先量的兩件事，都量完了，都對聯集有利**：

  | 文件 | 表格數 text → union | chart 候選 text → union |
  |---|---|---|
  | 1301-FY2023-AR | 180 → 223（+24%） | 104 → 67 |
  | 2412-FY2023-AR | 195 → 253（+30%） | 111 → 64 |
  | 2330-FY2023-AR | 193 → 260（+35%） | 33 → **7** |
  | 2330-FY2024-AR | 55 → 90（+64%） | 40 → **9** |

  1. **重複表格**：以「同一頁、重疊佔較小框 ≥ 50%」判定為同一張，
     保留**數字格較多**者（同數再比已填格數，再同則保留先跑的那一趟）。
     數字格優先的理由：把兩個數字欄併成一格的那一趟，總格數還是很體面，
     但它弄丟了一個數字 —— 那才是要排序的失效。
     重疊用「佔較小框的比例」而非 IoU：兩個 strategy 對同一張表的框法不同
     （`lines` 沿框線、`text` 沿墨跡），常常一個完全在另一個裡面，而 IoU 恰好懲罰這種情況。
  2. **chart 候選**：如預期大幅下降（最多 -78%），方向是**改善** ——
     D-020 已證明幾乎每個候選都是被誤判的表格。
     **關鍵檢查通過**：`2330-FY2023-AR` p7 與 `2330-FY2024-AR` p6
     （語料中唯一確認的 4 張真圖表）在聯集下**仍然是候選**，LOCK-0032／0033 沒有失去來源。

- **端到端驗證（透過 `extract_tables`，dev 已知數字）**：
  舊預設 `text` **0/9**，新預設 `union` **5/9**。
  單獨測 strategy 時是 0/15 vs 9/15，兩者比率一致（0% vs 約 60%）；
  分母不同只是兩次計數對「同頁多個數字」的歸併方式不同。

- **預設已改為 `union`**。這是對 candidate parser 的協議可見變更，
  依據建立在 **dev**（協議 1.3），且理由是**與 split 無關的**：
  沒有任一 strategy 支配另一個，所以「兩個都跑」不需要知道哪個 split 偏好哪一種；
  「只用 `lines`」則是對 dev 過度擬合，held-out 的 locked 數字（text 27/48 vs lines 10/48）正好證實這點。

  2. **candidate：方向相反，取更多反而變差**（10 → 8）。
     一個合理但**未驗證**的解釋：candidate 有 9,890 個 chunk（baseline 4,063），

- **⚠️ 上表有個陷阱，是我的設計錯誤，已修**：原本 `deep = top_k × multiplier`，

## D-030 `recall@k` 在兩個 parser 之間不可比，而 candidate chunker 有兩個實質缺陷

- **怎麼發現的**：D-029 裡 candidate hybrid 在 k=5／10／20 恆為 8/15，很反常。
  先懷疑是融合的 bug —— **查證後不是**（k 變大確實回傳更多 hit、涵蓋更多頁）。
  但那個查證的輸出暴露了別的東西：**同樣 5 個 hit，baseline 涵蓋 13 頁，candidate 只有 6 頁。**

- **我的指標有系統性偏差（這是最重要的一項）**：

  | parser | chunks | 字元中位數 | 頁/chunk 平均 | 總字元 |
  |---|---|---|---|---|
  | baseline | 4,063 | **800** | 1.57 | 3,247,578 |
  | candidate | 9,890 | **99** | 1.12 | 2,496,011 |

  在同一個 `top_k` 之下，**baseline 取回約 8 倍的字元量**（800 × k vs 99 × k）。
  `page-level recall@k` 因此**系統性偏好 chunk 較大的 parser** ——
  它同時獎勵「涵蓋更多頁」與「塞進更多內容」。
  **拿它比較 F0 與 F1，比的是 chunk 大小，不是檢索品質。**

  這與 D-017／D-020／D-028 是同一族的錯誤：我選了一個看起來合理的代理指標，
  它量到的不是我以為的東西。**D-029 的 parser 間比較必須降級為「不可比」**，
  同一 parser 內的 mode 比較（lexical vs dense vs hybrid）仍然有效 ——
  那些共用同一個 chunk 集合。

- **公平的比較方式** ✅ **已實作（2026-08-01）**：對齊**字元預算**而非 chunk 數。
  「給定 8,000 字元的 context，哪個 parser 的 chunk 裡含有證據」才是 F1 該回答的問題，
  而且那也正好對應真實約束（`num_ctx=8192`）。
  `recall_at_budget()`，`eval_retrieval.py` 同時輸出兩張表。三個決定各有一個測試釘住：

  1. **空白不計費。** 兩個 parser 的空白排版不同（layout 一格一行、baseline 整頁連在一起），
     去空白後全 corpus 是 2,161,264 對 2,161,561 字元 —— 內容相同，只差排版。
     讓空白計費就是在比排版。
  2. **重疊的文字算兩次費。** baseline 的固定視窗每 800 字元重疊 100，就該為此付費。
     這不是懲罰：預算花在重複遞送讀者已經有的文字上，就是花掉了；
     去重反而會為 baseline 的冗餘記功，而回答模型仍然得讀那些字。
  3. **跨過預算的那個 chunk 仍然算。** 排除它會讓指標又依賴 chunk 大小，只是方向相反 ——
     大 chunk 的 parser 會更常被丟掉最後、可能決定性的那一個命中。

  每個預算的比率都附上**那個預算買到幾個 chunk 的中位數** ——
  同一個預算在兩個 parser 上是不同的 chunk 數，而那正是預算要中和掉的東西，
  應該看得見而不是被隱含。單調性檢查也一併套到預算上：
  同一條排序清單取更多，不可能找到更少。

- **順帶量到 candidate chunker 的兩個缺陷**：
  1. **29% 的 chunk 不到 50 字元**（p5=18、p25=44、p50=99）。
     抽樣看內容是碎片，例如
     `'7.30\n新技術提供企業客戶數位轉型解決方案。此外，本公司積極 垶益報ꀥ率（%）'`
     與 `'1. 董事資料 > 85.6.11\n2,737,718,976'`。
     注意第一個裡的 `垶益報ꀥ率` 是**壞碼** —— 那是 2412 的字體問題（D-024）餵給 layout parser，
     parser 再據以切塊。**兩個缺陷在這裡疊起來了。**
     這種長度的 chunk 對生成幾乎沒有證據價值。
  2. **~~candidate 少掉 23% 的文字~~ → ~~14%~~ → 🔴 完全撤回：損失是 0%。**

     **去空白後兩個 parser 取回的內容完全相同：**

     | 比較 | 原始字元 | **去空白後** |
     |---|---|---|
     | baseline 區塊 | 2,840,051 | **2,161,561** |
     | layout 區塊 | 2,444,847 | **2,161,264** |
     | 比率 | 86% | **100.0%**（差 297 字元 = 0.014%） |

     **那個「損失」全部是空白與換行。** `get_text()` 產出的純文字帶有行間換行與對齊空白，
     dict-mode 的 span 文字沒有；兩者組裝方式不同，所以原始字元數本來就不該相等。

     **同一個錯誤我在這一條裡犯了三次，都是同一個形狀 ——

## D-031 heading 偵測把表格裡的每個小數當成頂層章節

- **怎麼發現的**：追 D-030 剩下的「29% chunk 不到 50 字元」。
  一路往上：回折被 section 不同擋住 → 99% 的小 chunk 在 **section 深度 1** →
  一份年報怎麼會有那麼多頂層章節？→ **看它們的名字**：

  ```
  1301-FY2023-AR: 1,083 個「頂層 section」，名稱是
                  '0.00' '0.0005%' '0.0036,204,112' '0.00中央化工'
  2330-FY2023-AR:   627 個，名稱是 '0.00' '0.00%' '0.001' '0.00106%'
  ```

  一份年報約有 **10 個**頂層章節。

- **根因（一個 regex）**：`_SINGLE_NUMBER = r"^(\d{1,2})[.、]"`
  會匹配 `0.00` 開頭的 `0.` → 回傳 level 1。
  **所以每一份財報裡的每一個小數，都變成了一個頂層章節。**
  既有的 `looks_tabular` 守衛抓不到它，因為 `0.00` 只有**一個**數字，
  而 `_MAX_FIGURES_IN_A_HEADING = 1` 允許 heading 含一個數字。

- **修正**：加一個否定前瞻 —— `r"^(\d{1,2})[.、](?!\d)"`。
  `0.00` 的 `0.` 後面接數字 → 拒絕；`1. 產品方面` 的 `1.` 後面接空白 → 接受。
  驗證過真 heading 全部仍然成立（`1. 產品方面`、`2、公司概況`、`1.2 明細`、
  `一、營運概況`、`壹、公司簡介`、`（一）財務狀況`、`10.結論`）。

- **效果**：

  | 文件 | 頂層 section | <50 字 chunk | chunk 中位數 |
  |---|---|---|---|
  | 1301-FY2023-AR | 1,083 → **518** | 32% → **13%** | 94 → **165** |
  | 2330-FY2023-AR | 627 → **180** | 26% → **9%** | 175 → **356** |
  | 2412-FY2023-AR | — → 424 | 20% → **9%** | 163 → **234** |

- **這不只是碎片問題，它打到 F1 的核心主張**：
  F1 說「chunk 帶有 section path，讓檢索與 citation 都有上下文」。
  當那個 path 是 `0.0036,204,112` 時，**那個主張是空的**。
  D-030 記的「6,515 個 section、83% 只含一個 chunk、29% chunk 不到 50 字」
  全部是這一個 regex 的下游後果。

- **順帶保留的另一個改善**：`_merge_undersized` 原本只合併 section path **完全相同**的相鄰
  chunk，而 `chunk_structure_aware` 每逢 section 變更就 flush ——
  所以它實際只能觸及「因長度被切開」的 chunk（實測每份文件觸發 79–293 次）。
  已放寬為**允許合併同一父節點下的兄弟 section**（`merge_siblings`），
  合併後的 section path 取共同父節點，所以 provenance 不會謊稱自己屬於其中一個。
  單獨計算它的效果：中位數 +28%、chunk 數 −10%，但 `<50 字` 比例幾乎不動 ——
  **真正的原因是上面那個 regex，這一項只是有用但次要。**

- **第二個 heading bug：`1.` 被判成 level 1，而它應該是 level 4。**

  修完小數之後仍有 518 個頂層 section。看它們的名字，發現兩件事疊在一起：
  1. **1301 的文字層也有壞碼**（含 `\x10` `\x16` 等控制字元），不只 2412。
  2. **真正的結構性錯誤**：臺灣財報的層級慣例是
     **壹／貳(1) → 一／二(2) → （一）(3) → 1./2.(4)**，
     而表裡 `(1)` 已經對到 4，`1.` 卻回傳 1。
     level 1 會**重設整個 section stack**，所以文件裡每一個編號清單都開了一個新的根。

  **測試編碼的是這個 bug** —— 六個測試斷言 `1.` → level 1，包括我幾分鐘前才寫的。
  我在改測試之前先量效果，確認哪一邊才對：

  | 文件 | 頂層 section | <50 字 chunk | chunk 中位數 |
  |---|---|---|---|
  | 1301-FY2023-AR | 1,083 → 518 → **22** | 32% → 13% → **2%** | 94 → 165 → **258** |
  | 2330-FY2023-AR | 627 → 180 → **56** | 26% → 9% → **9%** | 175 → 356 → **404** |
  | 2412-FY2023-AR | → 424 → **18** | 20% → 9% → **3%** | 163 → 234 → **322** |
  | 2882-FY2024-AR | → **10** | → **2%** | → 282 |

  **2882 剛好 10 個頂層章節 —— 那正是年報實際的壹～拾。**
  chunk 的深度分布也變成合理的金字塔（1→4 遞增）。所以測試是錯的，改動是對的。

  順帶一個讀起來奇怪但正確的結果：`1.2 明細` 是 level 2 而 `1. 概述` 是 level 4 ——
  帶點的形式明確指出自己在第二層，而裸的 `1.` 是層級最底的清單標記。

- **2330 剩下的 56 個頂層 section：查過了，不是 bug，是另一種編號體系。**

  台積電年報用**十進位編號**（`5`／`5.1 業務內容`／`5.2 技術領導地位`／`6.1 財務概況`），
  其他三份用 壹／一／（一）。那些裸的 `'5'` `'6'` `'7'` `'8'` 是**靠字體大小**偵測到的 heading
  （`detect_numbering_level` 回傳 `None`，因為沒有 `.` 或 `、`），
  所以它們的子項 `5.1`（level 2）找不到 level 1 的父節點，各自成了根。
  其餘是封面與目錄項（`'目錄'`、`'使命與核心價值'`、公司全名）—— 那些是真 heading。

  **不修**。要修需要「把 `N.M` 掛到前面那個裸 `N` 底下」的有狀態邏輯，
  而 `_SINGLE_NUMBER` 刻意要求 `.` 或 `、` 是因為裸數字曾在一份 707 頁報告裡
  造出 23,677 個假 heading（既有註解）。56 對 1,083 已經是可接受的殘量，
  換取一個新的、更容易出錯的狀態機不值得。**記錄為已理解的殘餘成本。**

- **⚠️ 現有 index 已過期，而重建需要 GPU**：
  chunk 邊界改了，`data/index/*/vectors.npy` 對應的是**舊的**切塊。
  `load_vectors(expect_rows=...)` 會擋下不一致，這是正確行為，
  但**我沒有重新產生 `chunks.jsonl`**，以免把可運作的索引弄成半壞狀態。
  **GPU 可用時要做：`build_index.py --gpu` 重建，然後重跑 BM25 與 `eval_retrieval.py`。**
  **D-029／D-030 的所有 recall 數字都對應舊切塊，重建後必須重量。**

  **⚠️ 更正（D-034，2026-08-01）：上面這段有兩個錯。**
  1. 「`load_vectors(expect_rows=)` 會擋下不一致，所以不會靜靜地用錯 index」**是假的**，
     因為 `eval_retrieval.py` 當時是 `np.load(...)` **直接讀檔、繞過 `load_vectors`** ——
     也就是說那道保險在**唯一會量 recall 的那條路上不存在**。過期的 index 在那裡不會 raise，
     它會為已經不存在的 chunk 交出看起來很有信心的數字。已改為走 `load_vectors`。
  2. 「重建需要 GPU」**也是錯的**。embedding 在 CPU 上跑得動：bge-m3 在 24 執行緒上
     每個 baseline chunk 825 ms、candidate chunk 601 ms，整個 corpus 約 2.6 小時。

## D-032 改讀文字流而不是格線，單格目標從 2/9 到 8/9（附一次差點在 locked 上調參）

- **起點是 D-028 的待辦第 1 項**：把被 pdfplumber 併成一張的多個附註切開。
  查證 `2330-FY2024-FS` p41 的完整結構後，發現該做的事比「切開」更根本。

- **p41 的真實結構（逐列印出，不是推測）**：整頁被當成一個 table 物件，裡面有
  存貨附註 ＋ 一段散文 ＋ 另一個小表 ＋ 整個權益法附註。而且
  **PyMuPDF 是一格一行**輸出的 —— 頁面讀起來是 `存 貨`、然後 `35,177,009`、
  然後 `34,511,032`。**標籤與數值不在同一列**，這是中文財報附註的常態版型，
  任何格線重建都救不回「哪幾行屬於同一個項目」。

  還有一件事：**合計列通常完全沒有標籤**，只有上方一條線。p41 的存貨合計
  287,868,810 就是這樣，它的數字併進了前一個明細（`物料及零件`）的數值列裡。

- **做法：`twfi/numeric/rows.py`，用人讀的方式讀，三條規則**：

  1. **期間表頭開啟一張表。** 一行只有期間標籤（`113年12月31日`、`112年度`）
     而沒有數字 → 那是表頭，它同時給出欄序與欄數。
     **同一頁出現第二個表頭就是切分點** —— D-028 要的「切開合併附註」不需要另一套
     啟發式，它是這條規則的副產品。p41 因此被正確切成 3 張表。
  2. **一列 = 一個標籤 ＋ 緊接其後的數字。** 同一行上的數字算，後續沒有自己標籤的
     行上的數字也算。
  3. **比表寬還寬的列其實是好幾列。** `k × width` 個數字在一個標籤底下就是 k 列，
     只有第一列有標籤 —— 其餘正是財報留白的續列與合計列。所以那個沒有標籤的
     存貨合計，從上方的附註標題（`十二、存貨`）伸手就拿得到（`resolve_page`
     跨表追一層，只追一層）。

- **量到的（dev 是唯一可據以調整的集合）**：

  | 集合 | 單格目標 | 表格路線 | 加上文字路線 | 與 gold 不符 |
  |---|---|---|---|---|
  | dev | 4 | 2 | **4** | 0 |
  | locked（held-out，只跑一次） | 5 | 0 | **4** | 0 |

  負債總計 129,035,061；`2330-FY2023-AR` p63 資產總額 5,532,371,215、

## D-033 壞字偵測器（第二版）：用普查寫白名單，並發現 dev 兩份文件都壞

- **為什麼有第二版**：第一版被我退掉，因為它用「看起來可疑的 codepoint 區間」黑名單，
  而那份黑名單在 U+2C00–2E7F 有個洞 —— **正好是我自己舉例那個字所在的位置** ——
  於是它把一份有大量壞頁的文件評為 0% 壞。
  **黑名單必須對「所有可能出現的區間」都判斷正確；白名單只需要對「實際出現的」正確。**

- **所以白名單是普查出來的，不是判斷出來的**：把 8 份可用文件全部 2,161,561 個
  非空白字元按 Unicode 區塊點過一遍。核心區間之外的佔比：

  | 文件 | 非核心佔比 | 形態 |
  |---|---|---|
  | 2412-FY2023-AR | **17.91%** | indic／cyrillic／thai／hebrew／greek 散佈 |
  | 1301-FY2023-AR | **15.45%** | latin-ext ＋ latin-1 ＋ 3.6% C0 控制字元 |
  | 2882-FY2024-AR | 0.29% | 幾乎全是 private-use，可能是 logo 字型 |
  | 2330-FY2024-AR | 0.10% | |
  | 2330-FY2023-AR | 0.05% | |
  | 2317-FY2024-FS／2330-FY2024-FS／2882-FY2024-FS | 0.00% | |

  兩份 15–18%，六份 ≤0.29% —— **五十倍的差距，門檻不是調出來的**。
  逐頁也分得開：乾淨的六份最差頁在 0.23%–2.73%，壞的兩份 p90 約 51%。
  **門檻取 5%**，落在中間。

- **「整塊放行 Latin」量過並否決**：放行 U+00C0–U+024F 會讓 1301 從 17.32% 掉到
  **8.09%** —— 因為它的壞碼正好集中在那個區間（Ǵ Ƕ Ȑ ȑ …）。
  文件層級還過得了門檻，但**逐頁會有大量頁掉到門檻下**，那正是第一版的假陰性。
  改成**逐字列舉**：乾淨六份在這些區塊只用了 14 種字元（®é×§öó°÷íÖ±Δäø，共 272 次），
  壞的兩份用了 **574 種**、每種數百次（`±` 合法出現 2 次、當亂碼出現 707 次）。
  逐字白名單讓壞的維持 15%／18%，乾淨的降到 0.00%–0.29%。
  **殘餘風險是便宜的那一種**：某份文件合法用了清單外的 ñ 或 €，只會讓那頁多一兩個字元，
  單獨不可能越過 5%，而被標記的頁會被人看。少一個**區間**才會藏起整頁壞掉的內容。

- **形態分開報，不併成一個旗標**：兩份壞的文件**壞法不同** ——
  一份散佈在無關文字系統（CMap 把 glyph 對到錯的 codepoint），
  一份是 Latin-1 區間加控制字元（位元流用錯編碼解讀）。補救方式不同，併成一個會丟掉有用的一半。

- **獨立驗證（這才讓它不只是自說自話）**：偵測器判 2317-FY2024-AR 100% 頁壞、
  2317-FY2023-AR 73% 頁壞 —— 而 `readable_ratio` 這個**完全不同的指標**獨立地把這兩份
  判為 `unusable_text_layer` 與 `partially_unusable_text_layer`。兩者一致。
  然後它抓出 2412 與 1301，而那個指標給它們 **95%／96% readable** ——
  因為它問的是「頁面有沒有產出字元」，不是「字元對不對」。

- **偵測器在一份乾淨文件裡只標了一頁，而那一頁是真的 —— 而且是第三種壞法。**
  `2882-FY2024-AR` p26（整份文件非核心字元僅 0.29%）被標記，15.0%，mode `private_use`。
  查證：那一頁有 **125 個同一個** private-use 字元 **U+F0FC**，
  而該頁是「董事會成員多元化政策之落實情形」的**矩陣表**。
  U+F0FC 是符號字型放進 private-use area 的標準位置（0xF000 + 0xFC），
  也就是說那 125 個字元**全部是打勾**。

  後果很具體：**列標題（董事姓名）與欄標題（金控／銀行／保險／財務會計／法律…）都讀得完美，
  但每一個打勾都不見了。** 讀這頁文字層的模型能列出董事、也能列出專業類別，
  **就是沒辦法說哪位董事具備哪一項**。

  這是第三種文字層失效，與另兩種都不同：不是整份字型對映壞掉，
  而是**一頁上用符號字型承載資料**。`mode` 欄位把它與亂碼分開，正是這個欄位存在的理由。
  （gold 沒有引用 p26，所以不影響現有題目 —— 但這屬於 report 該寫的可行性發現：
  **勾選矩陣對純文字管線是不可見的**。）

  **⚠️ 而且比率門檻對這一種壞法是錯的工具。** 查完 p26 後我去數全 corpus：
  **150 頁含 private-use 字元但都在 5% 門檻以下**，其中
  **`2882-FY2024-AR` 的 110 頁裡有 109 頁沒被標記**。
  也就是說「只報 p26」會漏掉同一份文件的另外一百零九頁。

  原因是兩種壞法的性質不同：亂碼是**瀰漫性**的，一頁要嘛壞要嘛不壞，比率是對的判準；
  private-use area **什麼字都沒有指派**，所以**每一個出現都是無法解讀的**，不管有幾個。
  一頁 2,000 字裡 5 個打勾 = 0.25%，遠低於門檻，但那 5 筆資料就是沒了。

  所以 `has_unreadable` 與 `garbled` **分開**：前者不看比率，後者看。
  全 corpus 現況：

  | 文件 | 含 PUA 的頁 | PUA 字元數 | 最多的一頁 |
  |---|---|---|---|
  | 2882-FY2024-AR | 110 | 693 | p26（125 個）|
  | 2412-FY2023-AR | 39 | 133 | p43（14 個）|
  | 1301-FY2023-AR | 20 | 216 | p42（125 個）|
  | 2330-FY2024-FS | 1 | 3 | p17（3 個）|

  **代價要看那個 glyph 原本是什麼**：董事專業矩陣裡的打勾是資料，
  頁首的 logo 不是。所以這一項**只報告不定罪**，並印出頁號讓人去看。

- **⚠️ 兩份新抓出來的文件就是 dev。**
  `2412-FY2023-AR` 與 `1301-FY2023-AR` 是 development set 的全部內容，
  也就是說**本研究所有的調參決策，都建立在這兩份文字層有 43%／48% 頁面損壞的文件上**。
  這是「dev 上的數字能代表什麼」的一項事實，不是可以修掉的缺陷 ——
  必須寫進 report 的限制，與 D-024 一併。

- **gold 沒有引用到任何一頁壞頁**：dev／locked／probe 三個集合共引用 71 頁，
  **亂碼頁 0 頁**。標註是看渲染圖做的，亂碼在圖上看得見也用不了，所以這件事大概從來沒真的有風險 ——
  但**沒有任何一處在強制它**，之後改一題就可能引到。
  `verify_gold_answers.py` 現在會把這種引用報成 `unverifiable` 而不是 `wrong`：
  答案可能完全正確，只是那個文字層壞到無法用來核對。

- **狀態**：ACCEPTED (2026-08-01)。`twfi/parsing/garbled.py` ＋ 14 個測試；

## D-034 兩個索引半邊共用一個 manifest 檔名，而 BM25 贏了；重建也不需要 GPU

- **怎麼發現的**：想確認「index 是否真的過期」時，比對 `chunks.jsonl` 與
  `vectors.npy` 的列數（4,063／9,890，兩邊相符），接著去讀 `manifest.json` 想核對
  `chunk_ids` —— 發現那個檔案裡寫的是 `k1` 與 `b`，
  `notes` 是「lexical half; dense vectors live beside this」。**那是 BM25 的 manifest。**

- **原因**：`save_vectors()` 與 `save_index()` **都寫 `data/index/<parser>/manifest.json`**。
  BM25 在向量之後建，所以它**覆蓋掉了 embedding 的 manifest** ——
  連帶把 model revision、dimension、以及能用來否決過期索引的 `chunk_ids` 一起消滅。
  每一個已建好的索引都是這個狀態。

- **修法**：兩邊各寫自己的檔名（`vectors.manifest.json` ／ `postings.manifest.json`）。
  `load_vectors` 另外認得舊形狀（自己的 manifest 不在、但有一個裸的 `manifest.json`），
  直接說「這個索引早於 manifest 分家，provenance 已被覆蓋，請重建」，
  而不是報一個一般性的檔案不存在。

- **更嚴重的另一半**：`eval_retrieval.py` 是 `np.load(directory / "vectors.npy")`
  **直接讀檔**。所以我在 D-031 與 PROGRESS 寫的那句安心話 ——
  「`load_vectors(expect_rows=)` 會擋下不一致」—— **在唯一量 recall 的那條路上是假的**。
  已改走 `load_vectors` 並在任何不符時 exit 2。

- **列數相符不等於同一批 chunk**：兩種切塊方式可能產出相同數量。
  兩邊 manifest 本來就各記了 `chunk_ids_head`，所以比對成本是零。
  `eval_retrieval.py` 現在會比，並且**在 manifest 沒有記 chunk id 時直接拒絕**
  ——「沒檢查過」不能報成「檢查通過」。

- **`build_index.py --device`（必填，無預設）**：量過 CPU 吞吐後發現 embedding 不需要卡。
  `cuda` 要刻意（CLAUDE.md 規則 8：別的專案可能正在用），
  `cpu` 也要刻意（那個速度下誤選會看起來像卡住）。
  CPU 上 dtype 預設 float32 —— 半精度在 CPU 是模擬的，只會更慢不會更省 ——
  而且那正好與 `eval_retrieval.py` 已經在 CPU 上用 float32 產生的 query 一致。

- **BM25 之前沒有建置腳本**：`postings.json` 與它的 manifest 就躺在 `data/index/*/`，
  而 repository 裡**沒有任何程式呼叫 `save_index`** ——
  它們是某個已經消失的 session 裡用臨時指令建的。
  **無法重新推導的產物不能支撐任何主張**，而 BM25 是 F0／F1 檢索的全部、F2 融合的一半，
  是兩個半邊裡最不能來歷不明的那一個。已補 `scripts/build_bm25.py`，
  它**讀 `chunks.jsonl` 而不重新切塊** —— RRF 是在共用的文件編號上依 rank 融合，
  在這裡重新切塊會讓兩個半邊悄悄對不上，而融合仍然會回傳結果。

- **狀態**：ACCEPTED (2026-08-01)。修正已進；CPU 重建進行中，完成後重跑
  `build_bm25.py` 與 `eval_retrieval.py`，D-029／D-030 的 recall 數字重量。

  - heading block 總量是 **135,916**，是我說的 74,090 的 **1.83 倍**，所以它不可能是那個差額。
  - **「chunker 不把 heading 放進 body」是錯的**：有 **74,618 字元的 heading path 留在 body 裡**。
  - 精確分解（剛好收斂到個位數）：
    `2,161,264 − 12,792（頁首頁尾）− 135,916（heading block）+ 74,618（殘留的 heading 行）= 2,087,174`
  - **真正把 heading 去乾淨之後是 2,012,556，剛好等於非 heading 的 content block —— 零遺失。**

- **⚠️ 那 74,618 是我自己的 bug**：`_merge_undersized` 把合併後 chunk 的 `section_path`
  改成兩者共同的**父層**，但 text 開頭仍然是 `_build` 當時寫的**更深的**路徑。
  也就是說 **1,515 / 4,796 個 candidate chunk（31.6%）宣告的 section 與自己第一行寫的不一致**。
  例：`2412-FY2023-AR:struct:00025` 宣告 `['致股東報告書','72.6 百萬分鐘']`，

  `section_path`。一個 chunk 的文字指向 A、自己聲稱在 B，那條 citation 會被拿去對錯的標題。
  已修（兩邊都先去掉自己的 heading 行，再寫回共同路徑，不變式由建構保證），

  **`2,087,174` 這個數字本身不代表任何量** —— 它是「字串剝前綴」在 31.6% 的 chunk 上失敗後的
  混合物。要 prefix-free 的總量請用 `include_heading_prefix=False` 重跑（2,012,556），不要剝字串。

### 被確認的三個

- **為什麼現在做**：`run_eval` 需要它，而它整層不存在。判分必須 deterministic
  （brief 明講「能 deterministic 評分的項目必須 deterministic」），所以沒有 judge model。

- **`twfi/eval/answers.py`**：§3.1 的七條正規化 ＋ §3.3 的六個指標
  （exact match、character-bigram F1、numeric with tolerance、unit、period、refusal
  precision／recall）。unit 與 period **與數字分開判**，因為 protocol 這樣要求，
  也因為它們抓的失敗很具體：**數字對但單位錯不是對的**，三者併成一個數就看不出哪個壞了。

- **兩個在實作中抓到的真 bug**：

  1. **民國年轉換把西元年也轉了。** `(?:民國)?(\d{2,3})年` 會在 `2023年` 裡匹配到 `23年`，
     把它改寫成 `3934年`。加 `(?<!\d)` 負向後查修正。
  2. **「530,738,356 千元」被當成 530,738,356 × 1000。**
     `千` 是 §3.1 rule 2 的放大詞，但這裡的 `千元` 是**單位**，而 gold 的數字本來就以千元表示。
     rule 2 的括號註解 **「保留原單位欄位另判」** 講的正是這件事。
     修法：比對前先把「與 gold `unit` 相同的結尾」剝掉，剝掉了就不套放大倍率；
     沒剝掉才套。所以 `1.2億`（unit=元）仍然展開成 120,000,000，
     而 `530,738,356 千元`（unit=千元）維持原值。
     **沒抓到的話，每一個把單位寫出來的正確數值答案都會被判錯一千倍。**

- **主要指標的定義**：數值題判**數字**（在宣告的 tolerance 內），其餘判 exact match；
  該拒答的題目判**有沒有拒答**。理由：對數值題用字串完全相同太脆弱 ——
  「資產總計為 530,738,356 千元」與「530,738,356」是同一個答案。

- **狀態**：ACCEPTED (2026-08-02)。38 個測試；`run_eval` 可以接了。

## D-041 撤回 D-040 的歸因：拒答幾乎都是對的，瓶頸是答案根本沒進到 prompt

- **D-040 我寫了「瓶頸是過度拒答，不是檢索」。那是錯的，方向相反。**

- **錯在哪**：我用**頁面層級的 `recall_at_5`** 當作「證據拿到了」的代理。
  但一頁會被切成好幾個 chunk，**檢索到的 chunk 涵蓋正確頁面 ≠ 它含有那個數字**。
  這正是 critic 早先指出的「page-level recall 過於寬鬆」——換個地方又咬了我一次。

- **改用直接的判準**：gold 答案裡的數字，有沒有**逐字出現在送進模型的 prompt 裡**。
  F3、dev 15 題：

  | | 題數 |
  |---|---|
  | 可回答題 | 13 |
  | **其中答案真的進到 prompt** | **5** |
  | 其中答案沒進到 prompt | 8 |

  拒答行為拆開來看：

  | 情況 | 題數 | 判定 |
  |---|---|---|
  | 證據在 prompt 裡卻拒答 | **1**（DEV-0009）| 真正的過度拒答 |
  | 證據不在 prompt 裡而拒答 | **6** | **正確行為** |
  | 證據不在 prompt 裡卻仍作答 | 2（DEV-0001、DEV-0007）| 幻覺／強答 |
  | 該拒答而拒答 | 2/2 | 正確 |

  **也就是說模型的拒答判斷幾乎是對的** —— 有證據就答（5 題裡 4 題作答），
  沒證據就拒答（8 題裡 6 題拒答）。`refusal precision` 看起來只有 0.22，

- **順帶：prompt 措辭幾乎不影響結果（假說被推翻）。**
  我原本懷疑 prompt 裡的「也不得推測」讓模型不敢讀表格數字。
  做了三個變體（`strict` / `permissive` / `verbatim`，只改「讀值算不算推測」的界線描述，

  | variant | 答對 | 拒答 | refusal precision |
  |---|---|---|---|
  | strict | 4/15 | 9 | 0.22 |
  | permissive | 4/15 | 9 | 0.22 |
  | verbatim | 3/15 | 8 | 0.12 |

  **strict 與 permissive 的總數完全相同**（逐題比對只有 1 題預測不同，
  且產物確實記錄了不同的 `prompt_variant`，所以不是沒接上）。
  **結論：這個模型在 temperature 0 下對這三種措辭不敏感，過度拒答不是 prompt 的問題。**
  這是一個有用的負面結果 —— 它把調 prompt 從待辦清單上劃掉了。

- **對後續的意涵**：要提高端到端正確率，該做的是讓答案更常進到 prompt，
  而不是勸模型多答。可行方向（依成本排序）：
  1. **F4 numeric route** —— DEV-0005／0006 是文件上根本沒印的衍生比率（34.55、65.45），
     只能算出來。這兩題永遠不可能靠檢索解決。
  2. 提高 `top_k_rerank`（目前 5）—— 但那是 protocol 2.5 凍結的常數，不能為了分數改。
  3. 切塊粒度 —— 一頁多個 chunk 時，含答案的那個未必進前 5。

- **量測本身要補一個診斷指標**：「答案是否出現在 prompt 中」比 page-level recall
  更接近生成端真正需要的東西。它不是 protocol 註冊的指標（所以不能拿來當 gate），
  但作為 error analysis 的診斷欄位應該留著。

- **狀態**：ACCEPTED (2026-08-02)。D-040 的數字保留，歸因已更正。

## D-043 typed router：先把 protocol 的 route 對照表讀錯，20% → 73.3%，然後停手
